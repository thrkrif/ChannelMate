# 6단계 릴리스 한계와 상태별 증거

6단계(모니터링 스택)는 사용자 결정으로 검증 범위를 줄여 마쳤다. 이 문서는 **무엇을 확인했고 무엇을 확인하지 않았는지**를 그대로 적는다.

**공개 문구**: 실제 외부 왕복 스모크 확인, C9 부분 검증, C10 일부 미달·나머지 미검증.

이 문구가 말하지 않는 것: 10개 합격 조건(AC)을 모두 충족했다는 뜻이 아니다. 하드웨어 표 6행이 모두 검증됐다는 뜻도 아니다. 실제 Grafana 발화가 Slack 리포트까지 이어지는 연속 경로, 합성 서명이 아닌 실제 Slack 이벤트 전달 경로는 이번에 확인하지 않았다(기존 스텁 검증을 재사용했다).

세부 수치와 원본 기록은 [`EXPERIMENT-LOG.md`](EXPERIMENT-LOG.md) §58·§59(후속 1~8)에 있다. 하드웨어 표는 [`../README.md`](../README.md)와 [`SETUP.md`](SETUP.md) 맨 위.

## 상태별 증거

| 항목 | 상태 | 증거와 한계 |
|---|---|---|
| 앱 구성 정상 답변(실제 Slack 왕복) | 확인(1건) | `scripts/rag-roundtrip` 1회: 수신 200, 답글 1개 5.1초. **합성 서명 멘션**이라 Slack이 이벤트를 보내는 경로는 검증하지 않았다. 호스트(bootRun) 구성의 실제 Slack 답변은 하지 않았다. |
| 알람 리포트 4종의 실제 Slack 게시 | 확인(각 1건) | `llm_final_failure`는 캡처 원본, 나머지 3종은 같은 형식의 **합성 변형**(규칙·심각도·역할·`startsAt`만 변경). 직송 3건 + n8n 경유 1건. 같은 본문 재전송은 게시 증가 0(중복 억제). |
| 실제 Grafana 발화 → Slack 연속 경로 | 미검증 | 알람 규칙 발화는 B3·B4 스텁 환경에서 확인했고 Slack 연속은 실제로 이어 보지 않았다. |
| n8n 경유 | 확인(1건) | `recovery_needed` 변형 1건. **잘못된 Credential 401·게시 0과 복원은 실행하지 않았다**(사용자 결정, 앱 직접 경로의 인증 실패 401은 M47/M48에서 검증). |
| Loki 조회, Grafana 대시보드 8패널 | 확인 | 로그 줄 조회와 패널 열림을 사용자가 화면으로 확인했고 쿼리 7개는 HTTP 수준 200. `검색 결과 분포`는 RAG를 꺼서 데이터 없음이 정상. |
| 리포트 금지 정보 점검 | 부분 확인 | 4종 모두 자동 패턴 검사 검출 0. **사람 눈 확인은 4건 중 1건**. |
| 별도 기기 LAN 차단(H1) | 확인(제한적) | 같은 Wi-Fi 휴대폰 1대에서 6개 포트(8080·3000·5678·9091·5672·5432) 각 5회 모두 닫힘. IPv6 해당 없음(전역 주소 없음), 토큰 요청은 포트가 닫혀 생략. |
| 알람 규칙 ①~④ 발화·비발화(C9) | 부분 검증 | ①·②: 호스트에서 각 5/5. ③: 발화 1/5(175.2초, 합격선 180초 이내·내부 예산 174초 초과), 2~5회 미실행, 비발화 5/5. ④: 발화(차단 5/5·부재 3/3)와 앱 30초 중단 통과, **비발화 공식 회차 1/5에서 모형 경계 초과로 멈춤**(보충 5/5는 대체 증거 아님). |
| 대시보드 값 vs 로그 집계(9.11) | 부분 검증 | 유효 창 2개에서 불일치 0. 관측 실패·부분 스냅샷 등은 해당 창이 없어 미검증. |

## 알려진 한계와 부채

1. **H1**은 휴대폰 1대·IPv4만 확인했고 IPv6와 토큰 요청은 하지 않았다.
2. 리포트 금지 정보 **사람 눈 확인은 1/4**다.
3. 캡처 규칙(`llm_final_failure`) 외 3종 리포트는 **합성 변형**이다.
4. n8n 경유 **잘못된 Credential**을 실행하지 않았다(C9.9 부분 검증).
5. **호스트 구성 정상 답변**은 실제 Slack에서 확인하지 않았다.
6. Loki 기본 조회에서 receiver·reactor 로그가 `backlog_snapshot` 줄에 묻힌다. 역할별로 따로 조회한다.
7. Alloy `tail_from_end` 때문에 Docker 재시작 이전 로그는 Loki에 없을 수 있다.
8. 28시간 가동 뒤 역할별 로그 파일이 약 25MB였다. 회전은 설정돼 있으나 장기 가동·영속성(재기동 뒤 상태)은 검증하지 않았다.
9. RabbitMQ `mem_limit` 512m이 OOM으로 죽은 적이 있다. 이때 `app_unobservable` 알람의 반응은 검증하지 않았다.
10. 알람 채널과 답변(테스트) 채널을 **같은 채널**로 놓고 검증했다. 분리 구성은 시험하지 않았다.
11. 스왑 증가 한계(≤512MiB) 초과(B1 +1,092, B3 +755, B4 +527.4MiB)는 측정 전부터 호스트 스왑이 6.7~11GiB 사용 중이던 상태의 영향으로 보이나 **원인은 확정하지 않았다**(환경 한계).

추가로 알려진 점:

- Linux, RAM 8GB 환경은 검증하지 않았다. 토큰 파일 권한 문제(Linux)도 시험하지 않았다.
- 하드웨어 측정은 echo 모델(모델 0)이다. 로컬 모델이 켜진 구성의 호스트 RAM은 측정하지 않았다.
- 검증 도구의 앱 모드 스텁은 `0.0.0.0`에 바인딩된다(검증 세션 한정, [SETUP](SETUP.md)의 알려진 부작용 참고).
- 해소 알림 재전송 시간을 10초로 줄인 부작용(D-15)이 있다([SETUP](SETUP.md)).
- 스모크 도중 Docker VM 재시작(사용자 자원 설정 변경 등)이 2회, RabbitMQ OOM 단일 컨테이너 재시작이 1회 있었다. 새 빌드·볼륨은 없었다.
- 클라우드 추론과 비용 가드(Anthropic 어댑터)는 7단계 계획이며 아직 없다.
