# 회고 — 5단계까지 한 장으로 (`v0.5.0`)

세부 수치와 근거는 [`EXPERIMENT-LOG.md`](EXPERIMENT-LOG.md)의 절 번호(§)로 연결한다. 여기에는 결론만 둔다.

## 무엇을 만들었나

Slack 멘션 → 수신 API(서명 검증·큐 저장 확인 후 ACK) → RabbitMQ → 워커(Ollama LLM, 선택적으로 RAG) → 스레드 답글. 같은 워커가 CloudWatch(SNS) 형식 알람도 받아 리포트를 올린다. 상태는 Postgres, 모든 LLM 호출은 OpenAI 호환 스키마다. 비용은 0원이다.

## 단계별 결론

| 단계 | 한 줄 결론 | 근거 |
|---|---|---|
| 1 (동기 P0) | Slack은 3초에 재전송한다. 실측하니 **2.5초 지연에서도 매번 재전송**이 발생했고 "2.5초는 안전하다"는 계획의 전제가 틀렸다. dedup을 끄면 중복 답글이 실제로 난다 | §5 |
| 2 (큐·워커) | 큐에 저장한 뒤 ACK하고, 처리 상태를 저장한 뒤 큐 ACK한다. 순차 20건에서 유실·실패·중복 0, **전송 결과 불명은 자동 재발신하지 않고 복구 대상으로 남긴다**(재발신하면 중복) | §15 |
| 2 후속 (기반 전환) | Redis 하나에 큐와 상태를 같이 둔 선택을 RabbitMQ + Postgres로 바꿨다. 포트/어댑터로 갈라 두었기에 교체 비용이 작았고 `ArchitectureTest`가 core의 오염을 빌드에서 막는다 | §16~§23, ADR-9 |
| 3 (RAG) | 임베딩 모델이 품질을 갈랐다. bge-m3 hit@3 24/24, nomic은 19/24. 임계값 0.54는 위쪽 여유가 0.01뿐이라 **다른 데이터에서는 흔들린다** | §31 |
| 4 (분류) | 구현은 끝냈지만 **기본 비활성으로 종결**. 16GB 노트북에서 3b와 7b가 서로를 축출해 모델 분리의 이득이 없었고, 회귀 기준(C4)은 정의 자체에 결함이 있었다 | §44~§46, ADR-10 |
| 5 (지표·n8n·설치) | 원인 구간(큐/LLM/RAG/전송)을 로그 집계로 볼 수 있다(기대 줄 수와 오차 0). n8n은 선택 어댑터로 **문서만**, Java 변경 0. Manifest로 만든 새 앱이 실제 멘션에 응답했다 | §47~§53 |

## 배운 것

1. **측정이 계획을 이긴다.** 2.5초 경계, 3b/7b 축출, 임계값 여유는 모두 계획 단계에서 틀렸거나 몰랐던 사실이다. 합격선을 먼저 고정하고 사후에 바꾸지 않는 규칙이 이걸 정직하게 만들었다.
2. **조용한 실패가 가장 비싸다.** 첫 멘션 무응답, 알람 채널 미초대(`not_in_channel`), 서버가 없을 때의 Request URL 검증 실패는 모두 Slack 화면에서는 원인이 안 보였다. 그래서 `env-check`와 SETUP의 "막혔을 때" 표를 만들었다.
3. **"완료"는 빌드 통과가 아니다.** 외부 왕복 성공과 오류 유도 후 기대 동작 확인으로만 완료를 판정했다(규칙 5). 이 기준이 기존 볼륨의 Flyway 체크섬 불일치 같은 환경 문제를 실측 단계에서 잡아냈다.
4. **문서가 길면 결론이 묻힌다.** 실험 기록이 1300줄을 넘었다. 단계마다 결론 한 줄을 이 파일에 올리는 습관이 필요했다.
5. **로컬 자원이 설계를 제한한다.** 16GB 한 대에서 Docker + Ollama를 같이 돌리니 모델 분리, 상시 가동, 동시 부하가 모두 제약이었다. 이 제약이 "무엇을 하지 않을지" 결정하는 데 도움이 됐다.

## 한계와 미검증

- 모든 알람은 **합성**이다. 실제 AWS 계정과 CloudWatch 서명은 검증하지 않았다.
- 5단계 사람 단계에서 **틀린 Credential 관찰, n8n 실행 출력 본문 재비교, 자리표시자 Request URL 수락 여부**는 하지 못했다(§53).
- RAG 임계값은 정답 없는 질문 2개로 정했다. 근거가 약하다(§31).
- 분류는 구현만 있고 기본 꺼짐이다. 의도 판독 11/12에서 사고형 장애 1건이 샜다(§46).
- 성능 수치는 합성 요청과 M1 16GB 한 대 기준이다.
